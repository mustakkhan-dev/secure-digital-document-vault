# BTech Major Project Viva & Defense Guide
## Project: Secure Digital Document Vault (AWS Cloud & DevOps)

---

### Q1: Why did you build "Secure Digital Document Vault" instead of using Google Drive or Dropbox?
**Answer**:
Basic cloud storage drives operate as general-purpose file hosting services. They lack:
1. **Granular revocation for pre-signed sharing links**: Standard pre-signed URLs remain valid until their cryptographic signature times out. If you generate a 2-hour link and regret it after 5 minutes, you cannot cancel it. In our architecture, the sharing link uses an intermediary token in DynamoDB (`isRevoked` flag), allowing instantaneous revocation.
2. **Automated, serverless lifecycle expiry alerts**: Using EventBridge and SNS, our vault automatically monitors expiring personal documents (passports, driving licenses, certifications) and sends preemptive notifications.
3. **Zero-Trust Auditability**: Every single view, download, or failed access attempt is logged with IP and User-Agent in DynamoDB without storing document content.

---

### Q2: What are Pre-Signed URLs and why are they used for uploads and downloads?
**Answer**:
A Pre-Signed URL gives temporary access to a specific private Amazon S3 object using cryptographic query string parameters generated by an IAM entity.
- **Why we use them**: If the user uploaded files directly through our backend API (API Gateway + Lambda), the entire 10MB binary payload would travel through Lambda memory, increasing execution latency, memory footprint, and AWS cost.
- **Our Flow**: The browser asks Lambda for a pre-signed URL (which takes 20ms). Lambda returns the signed URL. The browser then transfers the binary payload directly to S3 via an HTTP `PUT` request. The bucket remains 100% private to the outside world.

---

### Q3: What is the limitation of S3 Pre-Signed URLs, and how did your project solve it?
**Answer**:
- **The Limitation**: Once generated, an S3 Pre-Signed URL is completely stateless. It is mathematically impossible to invalidate or revoke a single pre-signed URL before its expiration time without revoking the parent IAM credentials (which would break the entire system).
- **Our Solution**: We generate an opaque UUID token (`shareId`) pointing to a DynamoDB record with attributes `expiresAt` and `isRevoked: false`. When an external user clicks the link, Lambda validates that `now < expiresAt` and `isRevoked == false`. Only if both are true does Lambda dynamically generate an ultra-short (2-minute) pre-signed download URL. If the owner clicks "Revoke", we update DynamoDB to `isRevoked: true`, immediately cutting off all future access attempts.

### Q4: How is user authentication handled? Does your database store passwords?
**Answer**:
No passwords or password hashes are ever handled by our database. We use **Amazon Cognito User Pools**:
1. Cognito handles user registration, password strength enforcement (min 8 chars, numbers, uppercase), and email verification with a 6-digit confirmation code.
2. Upon login, Cognito returns cryptographic JSON Web Tokens (JWTs): an `IdToken` and an `AccessToken`.
3. Our API Gateway features a **Cognito User Pool Authorizer** that cryptographically verifies the RS256 signature of the JWT before forwarding the request to Lambda.
4. Lambda extracts the immutable `sub` claim (Subject UUID) from the verified token context, guaranteeing that one user can never access or delete another user's documents.

---

### Q5: How is data protected at rest and in transit?
**Answer**:
- **In Transit**: All communication between client browser, API Gateway, Lambda, and S3 is strictly encrypted over HTTPS (TLS 1.3/1.2).
- **At Rest**:
  - In Amazon S3: Enforced with Server-Side Encryption (`AES256` or AWS KMS).
  - In DynamoDB: Encrypted at rest by default using AWS owned customer keys.
  - S3 Block Public Access is strictly enabled (all 4 settings turned ON: `block_public_acls`, `block_public_policy`, `ignore_public_acls`, `restrict_public_buckets`).

---

### Q6: Why did you choose DynamoDB over MySQL or PostgreSQL?
**Answer**:
1. **Serverless & Zero Maintenance**: DynamoDB has no servers to provision, patch, or keep running 24/7.
2. **On-Demand Pay-per-Request**: It scales to zero when not in use, making it completely free during development and college demonstrations.
3. **Single-Digit Millisecond Latency**: Key-value lookups for `userId + docId` and `shareId` occur in <5ms.
4. **Native Time-To-Live (TTL)**: Expired sharing records can be purged automatically by DynamoDB background processes without consuming write capacity.

### Q7: Explain your DevOps workflow and why GitHub Actions uses OIDC instead of AWS Access Keys.
**Answer**:
- Storing long-lived `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in GitHub repository secrets is a major security risk. If leaked or compromised, an attacker can access the entire AWS account.
- Instead, we use **GitHub Actions OpenID Connect (OIDC)**: GitHub acts as an Identity Provider. When the deployment pipeline runs, AWS Security Token Service (STS) assumes an IAM role with temporary credentials valid for only 1 hour.
- The pipeline automatically runs unit tests (`npm test`), validates Terraform templates, and applies infrastructure updates safely.
